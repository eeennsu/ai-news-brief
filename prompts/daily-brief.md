# 일일 AI 뉴스 브리핑 지시문

없는 뉴스를 지어내거나 확인하지 못한 기사를 넣는 것이 가장 큰 실패다. 확신이 서지 않는 기사는 넣지 않는다. 건수가 적거나 0건인 것은 실패가 아니다.

이 문서는 예약 작업 에이전트가 위에서부터 순서대로 따른다. 대화 맥락은 없다고 가정하고 쓴 문서이므로 이 문서와 레포의 파일만 근거로 삼는다.

## 목적

평일 아침 한국장 개장(9:00 KST) 전에, 밤사이 나온 AI 관련 뉴스 중 상장사 주가에 영향을 줄 만한 것을 골라 오늘 브리핑 JSON(`briefs/<date>.json`)을 만든다. 사용자는 한 명이고 매매 판단은 사용자가 한다. 브리핑은 참고 자료다.

## 공통 규칙

- 모든 명령은 레포 루트에서 실행한다.
- `node scripts/*.mts`를 실행하면 stderr에 `MODULE_TYPELESS_PACKAGE_JSON` 경고가 찍힌다. 오류가 아니다. 종료 코드와 stdout만 본다.
- 전체 실행을 재시도하지 않는다. 한 단계가 실패하면 그 단계의 지침대로 멈추고 끝낸다. 3회 제한은 7단계의 검증 오류 수정에만 쓴다.
- 파일을 쓰거나 고칠 때는 Write·Edit 도구를 쓴다.
- 시각은 모두 KST(UTC+9) 기준 ISO 8601 오프셋 표기(`2026-10-26T06:12:00+09:00`)로 쓴다. 세션 시계는 UTC다. 날짜와 현재 시각은 `date` 명령이 아니라 2단계의 `context.mts` 출력(`now`, `date`)을 쓴다.
- 이 문서에서 `<date>`는 2단계 출력의 `date`다.

## 1단계: 의존성 설치

```bash
pnpm install --frozen-lockfile
```

pnpm이 없으면(`command not found`) `corepack enable`을 실행한 뒤 위 명령을 다시 한다. 그래도 실패하면 아무것도 쓰지 않고 멈춘다. 실패 이유를 마지막 실행 요약에 적는다.

## 2단계: 컨텍스트 읽기

```bash
node scripts/context.mts
```

stdout은 JSON이다.

```json
{
  "now": "2026-10-26T07:40:12+09:00",
  "date": "2026-10-26",
  "tradingDay": true,
  "since": "2026-10-23T07:41:03+09:00",
  "previous": {
    "date": "2026-10-23",
    "generatedAt": "2026-10-23T07:41:03+09:00",
    "urls": ["https://..."]
  },
  "watchlist": {
    "holdings": [{ "market": "US", "ticker": "NVDA", "name": "엔비디아" }],
    "interests": []
  }
}
```

- `tradingDay`가 `false`면 브리핑을 만들지 않는다. 파일도 커밋도 알림도 없이 "휴장일 또는 주말이라 건너뛴다(`reason`)"를 출력하고 끝낸다.
- 명령이 0이 아닌 종료 코드로 끝나면(휴장일 목록이 올해를 덮지 않는 경우 포함) 오류 메시지를 그대로 출력하고 멈춘다. 개장일로 추측하지 않는다.
- `since`보다 늦게 발행된 기사만 쓴다. `previous`가 `null`이면 `since`는 24시간 전이다.
- `previous.urls`에 있는 기사는 이미 실렸으니 쓰지 않는다.
- `previous`가 있으면 `briefs/<previous.date>.json`을 Read로 열어 실린 사건의 `title`과 `summary`를 읽어 둔다. 4단계에서 같은 사건의 다른 URL 기사를 걸러 내는 데 쓴다.
- `watchlist`의 `holdings`는 보유 종목, `interests`는 관심 종목이다.

## 3단계: 수집

밤사이 미국 뉴스를 중심으로 `since` 이후에 나온 AI 관련 기사를 WebSearch로 모은다. 그 뉴스가 한국 관련주로 이어지는 영향까지 함께 본다.

검색어에는 날짜를 반드시 넣는다. 날짜 없는 검색어는 몇 년 전 기사를 앞에 준다. `since`의 날짜부터 `date`까지 각 날짜를 하루도 빼지 않고 검색어에 넣어 날짜마다 검색한다. 미국 날짜는 KST보다 늦으므로 `since` 시각의 미국 동부 날짜(KST 아침이면 그 전날)도 넣는다. 월요일이면 금·토·일·월 날짜가 모두 들어가고, 그 전 목요일 미국 날짜도 들어간다. 예(2026-10-26 월요일, `since`가 10-23 07:41 KST인 경우):

- `Nvidia AI chip news October 22 2026`, `... October 23 2026`, `... October 24 2026`, `... October 25 2026`, `... October 26 2026`
- `AI regulation export controls news October 25 2026`
- `semiconductor HBM data center news October 23 2026`

평일 화~금은 대개 어제와 오늘 두 날짜(와 미국 날짜)면 된다. 날짜를 넣어도 검색 결과의 제목이나 요약에 보이는 연도가 올해가 아니면 버린다.

### 포함 범위

상장사 주가에 닿는 경로가 있는 AI 뉴스만 대상이다. 아래 여섯 가지 중 하나에 들어야 한다.

1. 실적·가이던스(빅테크 capex 등)
2. 제품·모델·칩 발표
3. 규제·소송·수출 통제
4. 반도체·데이터센터 공급망(HBM, 전력 등)
5. M&A·투자 유치·IPO
6. 사고(데이터 유출, 대형 장애, 안전 사고)

각 범위를 한 번 이상 검색한다. 매일 같은 검색어만 쓰지 말고 그날 상황에 맞게 바꾼다.

### 제외

- 연구 논문
- SNS 화제성 데모·바이럴

### 보유·관심 종목 검색

`watchlist`의 종목 이름마다 `<종목 이름> AI news <월> <일> <연도>`처럼 날짜를 넣어 한 번씩 검색한다. 월요일이면 `since` 날짜부터 오늘까지를 포함하는 기간으로 검색한다. 목록이 비어 있으면 이 검색은 건너뛴다.

## 4단계: 확인

후보 기사마다 WebFetch로 원문을 열어 확인한다. 검색 결과 요약만 보고 넣지 않는다.

- 기사가 실제로 있는지, 제목이 무엇인지, 발행 시각이 언제인지 페이지에서 직접 확인한다.
- 페이지가 열리지 않거나(404·503·네트워크 오류 등), 열렸어도 발행 시각을 확인하지 못하면 그 후보를 버린다. 한 URL은 한 번만 연다. 안 열리면 다음 후보로 간다.
- 발행 시각에 시간대가 없으면 기사가 밝힌 시간대(ET, PT, GMT 등)로 해석해 KST로 바꾼다. 시간대를 알 수 없으면 버린다.
- 발행 시각이 `since` 이전이면 버린다. 날짜만 있고 시각이 없으면 `since` 이후인지 판단할 수 없으니 버린다.
- 발행 시각은 최초 발행 시각이다. 페이지에 수정 시각(Updated, Modified)만 보이고 최초 발행 시각을 모르면 버린다. 수정 시각을 발행 시각으로 쓰지 않는다.
- url이 `previous.urls`에 있으면 버린다.
- 같은 사건을 다룬 기사가 여럿이면 가장 원문에 가까운 하나만 남긴다(회사 발표, 통신사, 주요 매체 순).
- 직전 브리핑(2단계에서 읽은 `title`·`summary`)에 실린 사건의 후속 기사, 그리고 사건 발표가 `since` 이전인 기사는 URL이 새것이어도 그대로 쓰지 않는다. `since` 이후에 나온 새 사실(주가 반응, 새 숫자, 새 발언·결정)이 기사에 있을 때만 쓰고, 그때 `summary` 첫 문장을 그 새 사실로 쓴다. 새 사실이 없으면 버린다.
- 제목·`summary`·숫자·사실은 열어 본 페이지의 본문에 있는 내용만 쓴다. 기억이나 추측으로 보태지 않는다. 검색 결과 요약이나 다른 기사의 제목(추천 기사 목록 등)에서 본 숫자와 사실은 본문에서 확인하지 못했으면 쓰지 않는다. 관련 종목 연결만 예외다. 5단계 `stocks` 규칙을 따른다.
- 3단계의 포함 범위 여섯 가지 중 어디에도 들지 않거나 제외에 해당하면 버린다.
- 구체적인 사건을 다룬 기사만 쓴다. 시황 요약, 주간 회고, 전망, 칼럼, 투자 클럽 같은 의견 글, 여러 소식을 묶은 뉴스레터는 버린다.
- 다른 매체 기사를 옮겨 싣는 재게시 사이트(KuCoin, Tiger 같은 거래소·증권 앱의 뉴스 페이지, 뉴스 모음 사이트)는 원 출처 기사를 열어 확인한다. 원 출처가 열리지 않거나 원 출처의 발행 시각을 모르면 버린다.
- 로그인·구독이 필요한 기사(403, 유료 벽)는 열리지 않은 것으로 본다. 제목만 보고 넣지 않는다.
- 비상장사(Anthropic, OpenAI 등)가 주인공인 기사는 주가에 닿는 상장 종목이 5단계의 `stocks`로 분명히 이어질 때만 쓴다. 이어지지 않으면 버린다.
- 기준에 맞는 기사가 적은 날은 적게, 없으면 0건으로 쓴다. 기준을 낮춰 채우지 않는다.
- 회사 발표문과 공시(SEC 6-K·8-K 등) 원문 페이지도 기사로 쓴다. 제목과 발행 시각이 페이지에 적혀 있어야 한다. 출처 이름은 회사 이름으로 쓴다.
- 요약을 AI로 자동 생성했다고 밝힌 사이트는 쓰지 않는다.
- 발행 시각이 `GMT`·`UTC`·`EEST`·`GMT+9`처럼 시간대와 함께 적혀 있으면 그 시간대를 KST로 환산한다(예: 16:53 GMT는 다음 날 01:53 KST). 기사 본문의 "Thursday" 같은 요일만으로 시각을 정하지 않는다.

버린 후보의 수와 이유(열리지 않음, 발행 시각 불명, `since` 이전, 중복, 범위 밖 등)는 센다. 마지막 요약에 쓴다.

## 5단계: 작성

남은 기사로 `briefs/<date>.json`을 Write로 쓴다.

```json
{
  "date": "2026-10-26",
  "generatedAt": "2026-10-26T07:40:12+09:00",
  "items": [
    {
      "title": "기사 제목(원문 그대로)",
      "summary": "한국어 2~3문장 요약. 무슨 일이 있었고 시장에 왜 중요한지 쓴다.",
      "source": "매체 이름",
      "url": "https://example.com/article",
      "publishedAt": "2026-10-26T05:30:00+09:00",
      "stocks": [
        {
          "market": "US",
          "ticker": "NVDA",
          "name": "엔비디아",
          "verdict": "positive",
          "strength": "strong",
          "reason": "데이터센터 매출 가이던스가 시장 예상을 웃돌았다.",
          "watch": "holding"
        },
        {
          "market": "KR",
          "ticker": "000660",
          "name": "SK하이닉스",
          "verdict": "positive",
          "strength": "medium",
          "reason": "엔비디아 HBM 주 공급사라 가이던스 상향 수혜가 예상된다.",
          "watch": null
        }
      ]
    }
  ]
}
```

필드 규칙:

- `date`: 2단계의 `date`. 파일 이름도 `<date>.json`이다.
- `generatedAt`: 2단계의 `now`를 그대로 쓴다.
- `title`: 원문 제목. 외국어면 원문 그대로 둔다.
- `summary`: 한국어 2~3문장이다. 페이지에서 확인한 내용만 쓴다. 장중 수치는 "장중"이라고 적고, 종가는 기사가 종가라고 밝힌 경우에만 종가라고 쓴다(예: "22일 장중 약 7% 하락").
- `source`: 매체 이름(예: `Reuters`, `CNBC`).
- `url`: 4단계에서 연 https URL이다. 검색 결과의 추적용 리디렉션 URL이 아니라 기사의 최종 주소를 쓴다.
- `publishedAt`: 4단계에서 확인한 발행 시각. KST 오프셋 표기.
- `stocks`: 1개 이상. 미국 종목과 한국 관련주를 함께 짚는다.
  - 기사에 나온 종목은 기사 내용으로 판정한다.
  - 기사에 직접 나오지 않은 종목은 널리 알려진 공개 사업 관계(공급사, 고객사, 경쟁사, 같은 공급망)에 근거한 추론으로 붙일 수 있다. 이때 `reason`에 연결 고리를 적고("엔비디아 HBM 주 공급사"처럼), `strength`는 `weak` 또는 `medium`만 쓴다. `strong`은 기사가 그 종목을 직접 다룰 때만 쓴다.
  - 한국 관련주와의 연결이 분명한 뉴스에서는 한국 종목을 빠뜨리지 않는다. 연결이 억지스러우면 붙이지 않는다.
  - `market`: `US` 또는 `KR`.
  - `ticker`: KR은 숫자 6자리(`005930`), US는 대문자 1~5자(`NVDA`, `BRK.B`). `005930.KS`, `nvda`, `NASDAQ:NVDA` 같은 형식은 검증에서 걸린다.
  - `name`: 종목 이름.
  - `verdict`: `positive`(호재), `negative`(악재), `neutral`(중립).
  - `strength`: `weak`, `medium`, `strong`.
  - `reason`: 근거 한 줄.
  - `watch`: `watchlist.holdings`에 같은 `market`+`ticker`가 있으면 `"holding"`, `watchlist.interests`에 있으면 `"interest"`, 어디에도 없으면 `null`이다. 둘 다 있으면 `"holding"`이다. 감으로 정하지 않고 2단계 출력과 대조한다.
- 매매 행동 제안(매수 고려, 비중 축소, 관망 등)은 어디에도 쓰지 않는다. `reason`도 사실과 영향만 쓴다.
- 티커를 확신하지 못하면 그 종목을 뺀다. 종목이 하나도 남지 않으면 그 기사를 뺀다.

## 6단계: 순서와 건수

- 보유 종목(`watch`가 `holding`)이 걸린 뉴스를 먼저 놓는다. 그 안과 나머지는 각각 시장 파급력이 큰 순이다. 앞의 두 건이 알림 본문 Top 2가 된다.
- 최대 10건이다. 기준에 맞는 뉴스가 적으면 있는 만큼만 쓰고 억지로 채우지 않는다.
- 0건이면 `"items": []`로 쓴다. 0건 브리핑도 커밋한다. 알림이 오지 않은 날을 생성 실패로 읽기 위해서다.

## 7단계: 검증

```bash
node scripts/validateBrief.mts briefs/<date>.json
```

`OK`가 나오면(종료 코드 0) 다음 단계로 간다. 아니면 stdout에 `items[<i>].<field>: <메시지>` 형식으로 오류가 한 줄씩 나온다.

- 오류가 난 줄을 고치거나 해당 기사를 빼고 다시 실행한다. 고칠 수 있는 오류는 형식 문제(티커, 날짜 형식, `watch` 값, 순서)다.
- `publishedAt`이 `since` 이전이라는 오류, 이미 실린 URL이라는 오류가 난 기사는 고치지 말고 뺀다.
- 오류가 날 때마다 4단계에서 확인하지 않은 값으로 필드를 채워 넣지 않는다. 확인할 수 없으면 기사를 뺀다.
- 세 번 고쳐도 `OK`가 안 나오면 파일을 지우고(`rm briefs/<date>.json`) 커밋하지 않고 멈춘다.

## 8단계: 커밋과 push

```bash
git add briefs/<date>.json
git commit -m "chore: <date> 브리핑을 추가한다"
git push origin HEAD:main
```

클라우드 체크아웃의 로컬 브랜치 이름이 `main`이 아닐 수 있어 `HEAD:main`으로 push한다. push가 실패하면 `git pull --rebase origin main`을 하고 push를 한 번만 더 한다. 그래도 실패하면 멈춘다. 이때 9단계는 하지 않는다(알림이 먼저 나가면 앱이 파일을 못 찾는다).

## 9단계: 알림 발송

```bash
node scripts/sendPush.mts briefs/<date>.json
```

9:00 KST 컷오프, `origin/main`에 오늘 파일이 있는지 확인, 토큰 읽기는 스크립트가 처리한다. 종료 코드가 0이 아니면 출력된 메시지를 마지막 요약에 그대로 쓴다. 다시 실행하지 않는다.

## 10단계: 실행 요약

마지막에 아래를 출력한다.

- 브리핑 건수
- 버린 후보 수와 이유별 개수
- push 결과와 알림 결과(발송, 컷오프로 생략, 실패)
- 소요 시간(시작 시각과 끝 시각)
- 이상이 있었던 단계와 메시지
